## 1. 文档说明

### 1.1 本文解决什么

一期数据落在 JSON 文件（`backend/data/system/*.json`），仓储层为 `JsonEntityRepository` / `JsonStringEntityRepository`。本文把**当前 22 个活实体**（`backend/src/main/java/com/bsp/admin/**/domain/*.java`）逐字段翻译成达梦 DM8 的表结构，作为二期切换达梦的建表依据。

## 2. 建库前置约定（**建表前必须先落实，否则会出现中文截断**）

### 2.1 字符长度语义（**最关键的一条**）

达梦默认 **VARCHAR 按字节计长**，UTF-8 下 1 个汉字占 **3 字节**。若直接照搬「`VARCHAR2(50)` = 50 个汉字」的直觉，`产品研发一部`（6 字 = 18 字节）能存下，但 `permission.name` 最长的一条「基础数据增删改（字典/字段/枚举项）」（20 字 = 60 字节）就会被拦腰截断或直接报「列长度超出定义」。

| 方案 | 说明 | 本文取舍 |
|---|---|---|
| 建库参数 `LENGTH_IN_CHAR=1` | **2024 年 Q2 起达梦已废弃该参数**，DM8.4 显式指定会直接报 `Invalid parameter`；且旧版本下它的实际效果是「字节数放大 2~4 倍」，并非精确按字符 | ❌ 不可依赖 |
| **列级 `VARCHAR2(n CHAR)`** | 达梦官方给出的新版替代方案，**字段粒度**声明按字符计长 | ✅ **本文全部采用** |
| 长度值 ×3 预估 | 牺牲精度、易遗漏 | ❌ 不用 |

> **注意**：`CHAR` / `BYTE` 语义是**列级**属性，与实例参数无关，迁移与后续 DBA 操作都不会丢失该语义。

### 2.2 其余实例参数

| 参数 | 建议值 | 理由 |
|---|---|---|
| `CHARSET` | UTF-8（=1） | 全中文界面 + 中文人名/部门名 |
| `CASE_SENSITIVE` | 0 或 1 均可 | 本文 DDL **全部使用大写、不加双引号**，两种取值下均可正常解析；建议 0（大小写不敏感）以降低联调期踩坑 |
| `PAGE_SIZE` | 32KB | 官方推荐值，含 CLOB 列的表受益 |
| 超长记录 | 建议开启 | `sys_user.avatar`（data URL 上限 40 万字符）、`doc.content`、`chat_message.content` 均为 CLOB |

### 2.3 命名规范

| 项 | 规范 | 示例 |
|---|---|---|
| 表名 | 小写蛇形，**系统域加 `sys_` 前缀**，业务域/基础数据域/会话域不加 | `sys_user`、`module`、`dict_item`、`operation_log` |
| 列名 | **UPPER_SNAKE_CASE**（Oracle 惯例，不加双引号） | `CREATE_TIME`、`MODULE_ID` |
| 主键约束 | `PK_<表名>` | `PK_SYS_USER` |
| 唯一约束/索引 | `UK_<表名>_<列>` | `UK_SYS_USER_EMPLOYEE_NO` |
| 普通索引 | `IDX_<表名>_<列>` | `IDX_TASK_STATUS` |
| 检查约束 | `CK_<表名>_<语义>` | `CK_TASK_BELONG` |

**为什么系统域加 `sys_` 前缀**：`USER` 与 `ROLE` 是 Oracle/DM 的高风险关键字（`USER` 在 Oracle 中还是内置函数），裸用需处处加双引号，MyBatis-Plus 侧极易踩坑；同时该分组与现有数据目录 `backend/data/system/` 的划分一致。

### 2.4 保留字核实（**建表前请在目标实例上执行**）

达梦保留字清单**随版本变化**（8.1.3.x → 8.1.4.x 一次性新增 78 个关键字），且无法离线定论。请在目标实例上执行：

```sql
-- RESERVED = 'Y' 表示不可直接用作标识符；'N' 表示仅为关键字，可直接用作对象名
SELECT KEYWORD, RESERVED, RES_SQL, RES_PL, RES_SCHEMA, RES_VARIABLE, RES_ALIAS, RES_FIXED
  FROM V$RESERVED_WORDS
 WHERE KEYWORD IN (
   'USER','ROLE','MODULE','GROUP','DESC','LEVEL','TYPE','TIME','SORT',
   'OPERATOR','ACTION','TARGET','DETAIL','PATH','OWNER','TEST','HOURS',
   'STATUS','CODE','NAME','TITLE','CONTENT','CATEGORY','PRIORITY','WEEK','AVATAR'
 );
```

本文已**预先规避**下列高风险名（无需再论证，直接用规避后的名字即可）：

| 原始 Domain 字段 | 本文列名 | 规避原因 |
|---|---|---|
| `User`（表） | `sys_user` | `USER` 在 Oracle/DM 中为保留字（且是内置函数） |
| `Role`（表） | `sys_role` | `ROLE` 高风险保留字 |
| `*.desc` | `DESCRIPTION` | `DESC` 是确定的保留字（`ORDER BY ... DESC`） |
| `Org.level` | `ORG_LEVEL` | `LEVEL` 是 Oracle 保留字（层次查询伪列） |
| `Task.group` | `WORK_GROUP` | `GROUP` 是确定的保留字（`GROUP BY`） |
| `Role.type` / `Permission.type` | `ROLE_TYPE` / `PERM_TYPE` | `TYPE` 高风险 |
| `ChatMessage.role` | `MSG_ROLE` | `ROLE` 高风险 |
| `Log.time` | `OPER_TIME` | `TIME` 高风险（且语义更清晰） |
| `Log.module` | `BIZ_MODULE` | `MODULE` 高风险 |
| `Log.operator` | `OPERATOR_NAME` | `OPERATOR` 高风险 |
| `Task.week` | `WEEK_NO` | `WEEK` 高风险 |
| `*.sort` | `SORT_NO` | `SORT` 高风险；与 `WEEK_NO`/`LEVEL_CODE` 命名风格一致 |

若核实后发现仍有遗漏（`RESERVED='Y'`），四种处理手段按推荐顺序：

1. **改名**（本文采用的方式，代价最小）
2. **双引号包裹**：`CREATE TABLE "ADD"(...)` —— 但应用侧必须处处带引号，**不推荐**
3. **JDBC 连接串**：`jdbc:dm://ip:5236?keywords=(percent,top)` —— 仅影响该连接，适合局部应急
4. **服务端屏蔽**：`SP_SET_PARA_STRING_VALUE(2,'EXCLUDE_RESERVED_WORDS','LIST')` —— 全局生效且**需重启实例**，多应用共用实例时慎用；仅 `RES_FIXED=N` 的关键字可屏蔽

> 另注：`ROWID`、`TRXID`、`VERSIONS_STARTTIME` 等**即使加双引号也不能作为列名**，本文未使用。

## 4. 公共列约定

### 4.1 主键

**不使用 `IDENTITY` 或序列**，主键列就是普通 `NUMBER(19)` / `VARCHAR2(32)`：

- **Long 主键**：现状由 `JsonEntityRepository` 的 `AtomicLong` 在应用侧分配（启动时以文件内 `max(id)` 初始化）。保持应用侧分配 → 仓储实现可原样复用该逻辑，**Service 零改动**；且数据迁移时能原样带入存量 id。
- **String 主键**：现状由各 Service 生成（`TaskService.java:440-451` 的 `"task"+(max+1)`、`ProjectService.java:637-664` 的 `"p"+(max+1)`、`ModuleService` / `TopicService` / `DocService` 同理；`MenuOrder` 固定 `"menu-order"`）。

> **建库后可选的升级路径**（二期如希望改由数据库分配 id）：给各表主键加 `IDENTITY(1,1)` 或建序列。但**迁移期不建议**——IDENTITY 列能否显式插入存量 id 需先验证，而迁移必须保 id 不变（任务 `task7`、项目 `p1` 等 id 被日志 `target`、前端缓存引用）。
>
> ⚠️ **已知风险（需二期一并解决）**：应用侧 `max(id)+1` 在**并发插入时会重号**。一期 JSON 单实例 + 写锁掩盖了这个问题，入库后并发上来会暴露。建议二期改为「序列表 + 行锁」或数据库序列。16 号文档已记录同源的 id 复用风险。

### 4.2 审计列

| 列 | 类型 | 说明 |
|---|---|---|
| `CREATE_TIME` | `TIMESTAMP` | 创建时间 |
| `UPDATE_TIME` | `TIMESTAMP` | 更新时间 |

- **不加 `DEFAULT SYSDATE`，也不做自动更新**——现状由 Service 显式赋值（`LocalDateTime.now()`），保持零改动。
- Oracle 兼容模式下没有 MySQL 的 `ON UPDATE CURRENT_TIMESTAMP`，如后续要在库侧兜底，需用触发器（**本期不建议**）。
- 序列化格式：Jackson 配置为 `yyyy-MM-dd HH:mm:ss`（`JacksonConfig.java:19-27`），与达梦 `TIMESTAMP` 互转无歧义。

### 4.3 标志位

`NUMBER(1)`，取值 `0` / `1`，**不用 DM 的 `BIT`/`BOOLEAN`**——Java 侧是 `Integer`（如 `Dict.isBuiltin`、`DictItem.deleted`），`NUMBER(1)` 的驱动映射最稳。

### 4.4 逻辑删除

现状**只有 `dict` 与 `dict_item` 两张表有 `deleted` 列**（`grep getDeleted|setDeleted` 仅命中 `DictService`），其余全部物理删除。逻辑删除列定义为：

```sql
DELETED NUMBER(1) DEFAULT 0 NOT NULL   -- 0=正常  1=已逻辑删除
```

唯一约束需**排除已删除行**，普通 `UNIQUE` 做不到，本文改用**函数索引**（见 4.5）。

### 4.5 外键与约束策略

**不建物理外键**。理由：

1. 现状级联由 Service 显式编排且顺序已定型（删角色 → 先清 `role_permission` / `user_role`；删用户 → 清 `account`/`user_org`/`user_role`/`user_setting` 并把他人 `managerUserId`、`org.leaderUserId` 置空；删模块 → 先删任务和文档）；
2. `JsonEntityRepository.deleteById` 在记录不存在时**静默成功**（`:158-168`），若引入外键会变成抛异常，改变既有语义；
3. 批量删除依赖 `catch (Exception) 跳过`（`TaskService.java:576-582`），外键报错会改变行为。

因此**关联关系只在字段注释中标注为「逻辑外键 → 表.列」**，完整性由 Service 保证。

**可选**：若 DBA 坚持加外键，建议**先只加在同一事务内删除的强关联表上**（`sys_role_permission`、`sys_user_role`、`sys_user_org`、`sys_user_setting`），并在 Service 层验证通过后再推广；`task.parent_id`（自引用）、`sys_org.parent_id`（自引用）**不建议加**。

**检查约束**：只建议加一条，且需先清洗存量数据（见 9.5）：

```sql
-- 任务归属三选一：至多一个非空（2026-09-11 起「至少一个」由 Service 校验，因存量脏数据存在）
CONSTRAINT CK_TASK_BELONG CHECK (
    (CASE WHEN PROJECT_ID   IS NULL THEN 0 ELSE 1 END
   + CASE WHEN MODULE_ID    IS NULL THEN 0 ELSE 1 END
   + CASE WHEN TOPIC_ID     IS NULL THEN 0 ELSE 1 END) <= 1
)
```

### 4.6 Java 类型 → 达梦类型

| Java | 达梦（Oracle 兼容） | 说明 |
|---|---|---|
| `Long` / `long` | `NUMBER(19)` | 主键、外键 id |
| `Integer` / `int` | `NUMBER(10)` | 计数、工时、序号 |
| `Integer`（标志位） | `NUMBER(1)` | 0/1 |
| `Boolean` | `NUMBER(1)` | 仅 `UserOrg.isPrimary` |
| `BigDecimal` | `NUMBER(18,2)` | 仅 `Project.budget`（万元） |
| `String`（短） | `VARCHAR2(n CHAR)` | **必须带 `CHAR`**，见 2.1 |
| `String`（长文本） | `CLOB` | `doc.content`、`chat_message.content`、`sys_user.avatar` |
| `LocalDateTime` | `TIMESTAMP` | |
| `List` / `Map` | **拆子表** | 见第 6 节 |

## 5. 表结构明细

> 每张表的结构以 **DDL 为准**；字段表用于对照 Domain 来源。
> 「空」列：`N` = NOT NULL，`Y` = 允许 NULL。NOT NULL 的判定依据是 **DTO 的 `@NotBlank`/`@NotNull` + Service 业务必填校验**，与现状严格一致。

### 5.1 系统域

#### 5.1.1 `sys_org` 组织机构（← `Org`）

| 列 | 类型 | 空 | 默认 | 来源 | 说明 |
|---|---|---|---|---|---|
| `ID` | NUMBER(19) | N | — | `id` | 主键 |
| `PARENT_ID` | NUMBER(19) | N | 0 | `parentId` | 上级部门，顶级为 0 |
| `NAME` | VARCHAR2(50 CHAR) | N | — | `name` | 部门名称 |
| `CODE` | VARCHAR2(50 CHAR) | N | — | `code` | 部门编码，唯一 |
| `LEADER_USER_ID` | NUMBER(19) | Y | — | `leaderUserId` | 负责人，逻辑外键 → `sys_user.ID` |
| `SORT_NO` | NUMBER(10) | N | 0 | `sort` | 同层级排序 |
| `STATUS` | NUMBER(1) | N | 1 | `status` | 0 停用 / 1 启用 |
| `ORG_PATH` | VARCHAR2(500 CHAR) | Y | — | `path` | 祖先路径，如 `1/3/7` |
| `ORG_LEVEL` | NUMBER(10) | Y | — | `level` | 层级深度，顶级 1；Service 限制 ≤ 10 |
| `CREATE_TIME` | TIMESTAMP | Y | — | `createTime` | |
| `UPDATE_TIME` | TIMESTAMP | Y | — | `updateTime` | |

```sql
CREATE TABLE sys_org (
  ID             NUMBER(19)          NOT NULL,
  PARENT_ID      NUMBER(19)          DEFAULT 0 NOT NULL,
  NAME           VARCHAR2(50 CHAR)   NOT NULL,
  CODE           VARCHAR2(50 CHAR)   NOT NULL,
  LEADER_USER_ID NUMBER(19),
  SORT_NO        NUMBER(10)          DEFAULT 0 NOT NULL,
  STATUS         NUMBER(1)           DEFAULT 1 NOT NULL,
  ORG_PATH       VARCHAR2(500 CHAR),
  ORG_LEVEL      NUMBER(10),
  CREATE_TIME    TIMESTAMP,
  UPDATE_TIME    TIMESTAMP,
  CONSTRAINT PK_SYS_ORG PRIMARY KEY (ID)
);
CREATE UNIQUE INDEX UK_SYS_ORG_CODE   ON sys_org (CODE);
CREATE INDEX        IDX_SYS_ORG_PARENT ON sys_org (PARENT_ID);
CREATE INDEX        IDX_SYS_ORG_PATH   ON sys_org (ORG_PATH);      -- 树装配按 path 前缀匹配
CREATE INDEX        IDX_SYS_ORG_LEADER ON sys_org (LEADER_USER_ID);
CREATE INDEX        IDX_SYS_ORG_STATUS ON sys_org (STATUS);
```

#### 5.1.2 `sys_user` 人员档案（← `User`）

| `EMPLOYEE_NO` | VARCHAR2(50 CHAR) | N | — | `employeeNo` | 工号，唯一 |
| `MOBILE` | VARCHAR2(20 CHAR) | Y | — | `mobile` | 手机号，唯一（**空值不占唯一**） |
| `EMAIL` | VARCHAR2(100 CHAR) | Y | — | `email` | |
| `AVATAR` | **CLOB** | Y | — | `avatar` | data URL，Service 上限 40 万字符 → 必须 CLOB |

```sql
CREATE TABLE sys_user (
  ID              NUMBER(19)         NOT NULL,
```

```sql
  DICT_ID     NUMBER(19)         NOT NULL,
  CODE        VARCHAR2(64 CHAR)  NOT NULL,

  SORT_NO     NUMBER(10)         DEFAULT 0 NOT NULL,

  CONSTRAINT PK_DICT_ITEM PRIMARY KEY (ID)
);

    (DICT_ID, CASE WHEN DELETED = 0 THEN CODE END);
CREATE INDEX IDX_DICT_ITEM_STATUS ON dict_item (DICT_ID, STATUS, DELETED);
CREATE INDEX IDX_DICT_ITEM_SORT   ON dict_item (DICT_ID, SORT_NO, ID);

CREATE TABLE dict_item_ext (
  ID          NUMBER(19)         NOT NULL,
  ITEM_ID     NUMBER(19)         NOT NULL,
  DICT_ID     NUMBER(19)         NOT NULL,
  FIELD_CODE  VARCHAR2(64 CHAR)  NOT NULL,
  FIELD_VALUE VARCHAR2(500 CHAR),
  CONSTRAINT PK_DICT_ITEM_EXT PRIMARY KEY (ID)
);
CREATE UNIQUE INDEX UK_DICT_ITEM_EXT       ON dict_item_ext (ITEM_ID, FIELD_CODE);
CREATE INDEX        IDX_DICT_ITEM_EXT_VAL  ON dict_item_ext (DICT_ID, FIELD_CODE, FIELD_VALUE);
```

> ⚠️ **动态唯一约束无法用唯一索引表达**：`dict_field.isUnique=1` 时要求「同字典 + 同字段 + 同值」唯一，但还须**排除已逻辑删除的字典项**（`DictService.java:396-409`）——`dict_item_ext` 看不到 `dict_item.deleted`，唯一索引会误伤已删除项。**因此应用层校验仍是唯一权威**，`IDX_DICT_ITEM_EXT_VAL` 仅作查询加速（**非唯一**）。若要下沉到库侧，需在 `dict_item_ext` 上再冗余 `ITEM_DELETED` 列并做函数索引——收益不大，**不建议**。

| 10 | `UserSetting.payload` | `Map<String,Object>` | `sys_user_setting_item` | **EAV + `.` 路径表达嵌套** |

### 6.1 拆表带来的三项强制改造

拆表**不是免费的**，以下三处在仓储层必须补齐，否则读写都会错：

1. **有序性**：`M` 中的 `rd`/`stakeholders`/`options`/`paths` 是**有序数组**，读取时必须 `ORDER BY SORT_NO` 还原顺序，写入时按下标回写 `SORT_NO`。漏掉排序会导致「研发负责人顺序每次刷新都在变」。
2. **读写的原子性**：父表保存需同时重建子表行（现状是「整份替换」语义）。若沿用 `EntityRepository` 接口，`updateById` 内需包在**同一事务**里（一期 JSON 无事务，二期正好补上）。
3. **全量替换而非增量**：现状 `UserService.saveRelations` 就是「先 `deleteIf` 再逐条 `insert`」的全量替换口径，子表沿用同一口径最省事，但会产生大量 delete/insert（如 `sys_user_org`）。

### 6.2 与「Service 零改动」目标的冲突（**必须评审**）

`技术设计文档.md:240` 承诺「新增 `DmRepositoryImpl` 适配 `EntityRepository` 接口，**Service / Controller / DTO 零改动**」。但拆子表后：

- `EntityRepository<T>` 的方法签名只吃**一个实体对象**，仓储内部要额外维护 10 张子表；
- 现有 Service 大量代码**直接读写 `List`/`Map` 字段并做内存过滤**（如 `ModuleService.list` 按 `rd` 判定数据可见性、`DictService` 按 `dictField` 校验 `ext`、`RoleService` 读 `customOrgIds`）。这些字段在拆表后必须由仓储层**装配回实体对象**，否则 Service 会拿到 `null`。

**结论**：拆子表**在存储层内部实现是可行的**（仓储负责「实体 ↔ 主子表」双向转换，Service 仍看到完整的 `List`/`Map`），但代价是仓储层复杂度显著上升，且 `EntityRepository.findByCondition` 的条件查询无法直接下推到子表列（如「按研发负责人筛选模块」仍需内存过滤或另写 SQL）。

**建议的取舍**（详见 9.1）：**只对有关联语义与查询价值的字段拆表**（`sys_role_custom_org`、`menu_order_path`、`dict_field_option`），其余「纯展示型有序列表」保留单列 CLOB 存 JSON 字符串。

### 7.2 设计说明

- **一期是内存过滤，二期索引要重新校准**。`RowFilters`（`common/filter/RowFilters.java`）的所有条件都作用在**已加载到内存的集合**上，`JsonEntityRepository.findByCondition` 甚至是死代码（无调用方）。因此现有代码**无法反推出真实的 SQL 查询形态**——上表索引是**按业务语义预估**的，二期压测后需按实际执行计划调整。

- **达梦的 `DESC` 索引**：`IDX_OPERATION_LOG_TIME` 按升序建即可，达梦支持反向扫描，无需额外建降序索引。

## 9. 已知冲突与待确认项（**需评审后再实施**）

### 9.1 【高】集合字段拆子表 vs 「Service 零改动」

**冲突**：`技术设计文档.md:56` 明确「一期**必须做**：存储层抽象，保证二期切换达梦时 Service 层零改动」；`:240` 再次承诺「Service / Controller / DTO 零改动」。而拆子表要求仓储层做「实体 ↔ 主子表」双向装配，且 `EntityRepository.findByCondition` 无法下推子表列。

**代价**：仓储层复杂度上升；「按研发负责人筛选模块」这类查询要么内存过滤，要么另写 SQL。

**建议**：**收敛拆表范围**——只拆有真实关联语义与查询价值的（`sys_role_custom_org`、`menu_order_path`、`dict_field_option`），其余展示型有序列表（`rd`/`stakeholders`/`ext`/`payload`）保留单列 CLOB 存 JSON 字符串。若坚持全拆，请在评审时同步修订 `技术设计文档.md:240` 的「零改动」承诺。

**待确认**：⬜ 全拆 / ⬜ 收敛拆表（推荐）/ ⬜ 全部用 CLOB

### 9.2 【中】业务表存的是字典**显示名**，而 14 号文档要求存 **code**

**冲突**：`14-基础数据.md:53,172`「业务表存 `字典 code + 字典项 code`，不存显示名、不存字典项 id」；但**实现存的是中文显示名**——`project.json` 里 `"status": "完成"`、`"level": "D"`、`task.json` 里 `"priority": "中"`。

**影响**：表结构本身不受影响（都是 `VARCHAR2(64 CHAR)`），但**含义完全不同**：

| 口径 | 改名「在建」→「建设中」时 | 存量数据 |
|---|---|---|
| 存 code（文档要求） | 业务数据零影响 | 显示名自动跟随 |
| 存 name（现状） | **存量数据全部变成悬空值**，需批量 UPDATE | 显示名与数据耦合 |

**建议**：**入库前定口径**。若改存 code，需同步改造全部 Service 的字典读写（`ModuleService` / `TopicService` / `ProjectService` / `TaskService` 的 `status`/`priority`/`product`/`category` 处理）+ 存量数据转换脚本。**这是本次表结构设计中影响面最大的一项待确认。**

**待确认**：⬜ 维持现状（存 name）/ ⬜ 改为存 code（对齐 14 号文档，需额外改造）

### 9.3 【中】`Module.rd` 是数组，`Project.rd` / `Subsystem.rd` 是单值

同一业务语义「研发负责人」在三处类型不一致：

| 实体 | 类型 | 本文落法 |
|---|---|---|
| `Module.rd` | `List<String>` | `module_rd` 子表 |
| `Topic.rd` | `List<String>` | `topic_rd` 子表 |
| `Project.rd` | `String` | `project.RD` 单列 |
| `Subsystem.rd` | `String` | `subsystem.RD` 单列 |

前端 `api.d.ts` 如实镜像（`ModuleItem.rd: string[] | null` vs `ProjectListItem.rd: string | null`），**不是前端 bug，是后端本身不一致**。

**待确认**：⬜ 保持现状 / ⬜ 统一为多值（Project/Subsystem 也拆子表，前后端需同步改）

### 9.4 【中】`Project.startDate` / `endDate` 是 String 且零校验

现状：`Project.java:61,64` 声明为 `String`，Service 只做 `trimToNull`，**无任何格式校验**——任意字符串都能入库。本文按现状建为 `VARCHAR2(10 CHAR)` 以保 1:1 平移。

**风险**：迁移时若直接改 `DATE` 会因存量脏值报错。

**建议的数据治理路径**：迁移前清洗（正则 `^\d{4}-\d{2}-\d{2}$` 校验，非法值置 NULL）→ 业务侧补格式校验 → 二期再改 `DATE`。`Task.deadline` / `Task.planDate` 已有正则校验（`TaskService.java:422-429`），本次一并保持 VARCHAR2。

**待确认**：⬜ 按现状 VARCHAR2 + 后续独立治理（推荐）/ ⬜ 本次直接建 DATE 并在迁移前清洗

### 9.5 【低】存量脏数据：`projectId = "undefined"`

`backend/data/system/task.json` 中 `task4` / `task7` 的 `projectId` 是字符串 `"undefined"`（16 号文档已登记，来源为历史联调数据，非本期代码产生）。

**影响**：若启用 `CK_TASK_BELONG` 检查约束，`"undefined"` 是**非 NULL 值**，会被计入「非空归属」，与真实归属冲突导致约束失败。

**建议**：迁移前清洗这两条（置 NULL 或改指真实项目），**清洗通过后再启用检查约束**。本文 DDL 中该约束默认注释掉，即为此故。

### 9.6 【低】`chat_message.content` 存在隐性 300 字符截断

`ChatService.java:278` 读取 SSE 请求体时 `sb.length() > 300 ? sb.substring(0, 300) : sb`，**用户消息超过约 285 字符会被静默截断**，与 17 号文档「无长度上限」「以落库内容为准」冲突。

**影响**：仅影响功能正确性，不影响表结构（本文已建 `CLOB`）。

**建议**：二期一并修复（该截断疑为读取 SSE 请求体时误用固定缓冲）。**待确认**：⬜ 本次记录、二期修复

### 9.7 【低】`operation_log` 无保留期

15 号文档全文无日志 TTL / 条数上限 / 归档策略，后端也无裁剪逻辑，该表**无限增长**。

**建议**：入库后由 DB 侧定时任务清理（如保留 12 个月）或按 `OPER_TIME` 做范围分区。**待确认**：⬜ 保留期 = ____ 个月

### 9.8 【低】MyBatis-Plus 命名映射需显式开启

本文列名为 `UPPER_SNAKE_CASE`，Java 为 `camelCase`，需在二期配置：

```yaml
mybatis-plus:
  configuration:
    map-underscore-to-camel-case: true   # CREATE_TIME → createTime
  global-config:
    db-config:
      table-prefix: ~                    # 不加前缀，表名用 @TableName 显式声明
```

⚠️ 注意两处**特例列**，映射后与 Java 字段名不一致，需在实体上 `@TableField` 显式指定：

| Java 字段 | 列名 | 说明 |

| `desc` | `DESCRIPTION` | 规避保留字 |
| `level` | `ORG_LEVEL`（Org） / `LEVEL_CODE`（Project） | 规避保留字 |
| `group` | `WORK_GROUP` | 规避保留字 |
| `type` | `ROLE_TYPE` / `PERM_TYPE` | 规避保留字 |
| `sort` | `SORT_NO` | 规避保留字 |
| `week` | `WEEK_NO` | 规避保留字 |
