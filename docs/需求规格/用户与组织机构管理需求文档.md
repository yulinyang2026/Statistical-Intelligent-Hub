# 用户与组织机构管理体系 需求文档

**版本：v1.1** ｜ 适用范围：单租户中小后台（组织/人员百级数据量） ｜ 文档类型：功能与数据设计需求

> **规模定位**：本系统组织数与人员数均为百级（部门约 10–100，人员约 50–500，角色约 10–50）。设计遵循**轻量优先**：单库单表、`parent_id + path` 描述组织树，不引入闭包表、分库分表、多租户隔离。

> **v1.1 已确认边界**：① 单租户，不考虑多租户；② 不设置岗位层，角色直接挂人；③ 登录方式仅「账号 + 口令」；④ 数据范围需支持「本人 + 直属下属」；⑤ 需要操作审计日志与登录日志。

---

## 1. 概述与目标

### 1.1 背景
管理后台需要统一管理「谁（用户）」「在哪个部门（组织）」「能做什么（角色/权限）」。规模较小，重点是关系清晰、可维护、可审计，而非高并发性能。

### 1.2 术语定义

| 术语 | 含义 |
| --- | --- |
| 组织 / 部门 | 层级结构单元，可多级嵌套 |
| 用户 / 人员 | 系统中真实个人档案，含直属主管 |
| 账号 | 登录凭证 = 用户名 + 口令（一人一账号） |
| 角色 | 权限集合，直接分配给用户 |
| 权限 | 最小授权单元：菜单、接口、数据三类 |
| 数据范围 | 角色可见数据的部门/人员边界 |

---

## 2. 总体设计原则

- **单租户**：所有表不带 `tenant_id`，不做租户隔离。
- **账号与人员分离**：人员档案 `user` 与登录账号 `account` 拆开（当前仅口令一种，结构上仍保留扩展位）。
- **角色直接挂人**：角色通过 `user_role` 直接分配给用户，不设置岗位层。
- **一人多部门用关系表**：用 `user_org` 承载用户—部门关系，`is_primary` 标记主属部门。
- **删除策略**：日常「移除人员」走**逻辑删除**（停用/离职，保留档案与历史引用）；**2026-09-11 起另提供「删除」做物理删除**（连账号与部门/角色绑定一并移除），用于清理建错账号、测试账号。本工程任务/模块/项目引用的是**姓名**而非用户 id，日志存「名称(id)」字符串，故物理删除不破坏既有数据。
- **轻量优先**：单库单表，`parent_id + path`，普通索引。

## 3. 组织机构管理

### 3.1 功能需求
- **[ORG-01]** 维护部门树：新增、编辑、删除、移动部门。
- **[ORG-02]** 树形展示与展开/折叠，支持按名称、编码搜索。
- **[ORG-03]** 设置部门负责人、部门排序、部门状态（启用/停用）。
- **[ORG-04]** 部门合并/调整时，其下人员可批量转移到目标部门。

> **实施留痕（2026-09-09，来源：会话提问确认「补齐两个弹窗」）**：按 [ORG-01]/[ORG-03]/[ORG-04] 补齐前端 `src/views/org/modules/org-dialog.vue`（新增/编辑/移动部门：上级部门树选择〔顶级虚拟根节点〕、名称、编码、负责人下拉、排序、启用状态）与 `src/views/org/modules/transfer-dialog.vue`（人员批量转移：源部门只读展示、目标部门树选择〔剔除源部门自身〕、转移提示）。字段口径与 `02-数据模型.md`、`frontend/src/types/api/api.d.ts`（`Org.OrgSaveParams` / `Org.OrgTransferParams`）一致，无需求口径变更。

### 3.2 数据字段

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | bigint | 主键 |
| parent_id | bigint | 上级部门，顶级为 0 |
| name | varchar | 部门名称 |
| code | varchar | 部门编码，唯一 |
| leader_user_id | bigint | 部门负责人（可空） |
| sort | int | 同层级排序 |
| status | tinyint | 0 停用 / 1 启用 |
| path | varchar | 祖先路径，如 `1/3/7` |
| level | int | 层级深度 |

### 3.3 业务规则
- 删除部门前必须「无子部门」且「无在职人员」，否则提示先转移。
- `path` 新增/移动/重命名时全量重算整棵树（百级数据开销可忽略）。
- 建议层级深度 ≤ 10；停用部门不删除，历史数据仍可见。

## 4. 角色与权限管理

### 4.1 功能需求
- **[ROLE-01]** 角色 CRUD：新增、编辑、删除（内置角色不可删）、启用/停用。
- **[ROLE-02]** 角色授权：勾选菜单、接口、数据三类权限。
- **[ROLE-03]** 设置数据范围（见 4.3，含「本人 + 直属下属」）。
- **[ROLE-04]** 角色直接分配给用户（`user_role`）。
- **[ROLE-05]** 内置角色（超级管理员、普通员工）随系统初始化。

> **实施留痕（2026-09-09，来源：会话需求「部门/用户/角色管理不完整或打不开，请修复」）**：补齐前端 `src/views/role/index.vue`（列表：类型/数据范围/挂靠人数/状态 + 新增/编辑/删除）与 `role-dialog.vue`（内置角色名称编码锁定）、`assign-dialog.vue`（授权：菜单/接口/数据三类权限树勾选 + 数据范围 6 档 + 自定义部门）。删除内置角色前端拦截并提示（`builtinRoleDeleteTips`）。字段口径与 `02-数据模型.md`、`Api.Role.*` 类型一致，无需求口径变更。

### 4.2 数据字段

| 表 | 字段 | 说明 |
| --- | --- | --- |
| role | id, name, code, type, data_scope, remark, status | type：内置/自定义 |
| permission | id, code, name, type, parent_id | type：menu/api/data |
| role_permission | role_id, permission_id | 角色-权限关联 |
| user_role | user_id, role_id | 用户-角色直接关联 |

### 4.3 数据范围类型（data_scope）

| 值 | 名称 | 可见数据边界 |
| --- | --- | --- |
| 1 | 全部数据 | 不附加过滤 |
| 2 | 本组织及下级 | `dept_id` 在本人主属部门及其子树 |
| 3 | 仅本组织 | 仅本人主属部门 |
| 4 | 仅本人 | 仅本人创建的数据 |
| 5 | 本人 + 直属下属 | 本人数据 ∪ `manager_user_id = 本人` 的直属下属的数据 |
| 6 | 自定义部门集合 | 指定的部门集合 |

> 新增：**「本人 + 直属下属」** 依赖用户上的 `manager_user_id`（直属主管）字段，解析时取 `manager_user_id = 当前用户` 的用户集合，再并入其数据。

### 4.4 业务规则
- 权限码集中维护，禁止在业务代码硬编码。
- 禁用角色后，其成员权限立即失效。
- 用户最终权限 = 所挂全部角色的权限并集。

## 5. 用户与账号管理

### 5.1 功能需求
- **[USER-01]** 人员档案 CRUD：姓名、工号、手机、邮箱、直属主管、状态。
- **[USER-02]** 账号管理：账号 + 口令，支持密码重置。
- **[USER-03]** 部门归属：设置主属部门与兼职部门。
- **[USER-04]** 启用/禁用；离职处理（禁用并解绑主属，保留历史）。

> **实施留痕（2026-09-09，来源：会话需求「部门/用户/角色管理不完整或打不开，请修复」）**：补齐前端 `src/views/user/index.vue`（列表：部门归属标签/角色/直属主管/启停开关/离职）+ `user-dialog.vue`（人员档案、账号口令、直属主管、主属与兼职部门、角色分配）+ `reset-password-dialog.vue`（重置密码）。字段口径与 `02-数据模型.md`、`Api.User.*` 类型一致（`manager_user_id` 防成环由后端校验），无需求口径变更。

### 5.2 数据字段

| 表 | 字段 | 说明 |
| --- | --- | --- |
| user | id, name, employee_no, mobile, email, manager_user_id, status | 人员档案，含直属主管 |
| account | id, user_id, username, auth_type, credential, status | 口令登录；credential 为加盐哈希 |
| user_org | user_id, org_id, is_primary | 一人多部门关系 |

### 5.3 业务规则
- 用户业务主键统一用 `user_id`，禁止用 username 当业务主键。
- 同一用户仅一个 `account`，`username` 唯一；手机号可作为联系信息但当前不作为登录名。
- `user_org` 中每个用户 `is_primary` 有且仅有 1 个为 true。
- `manager_user_id` 形成主管链，禁止成环（保存时校验）。
- 离职：禁用 user + account，解除主属；历史单据 `created_by` 保留。
- 口令使用 bcrypt / Argon2 加盐哈希，禁止明文或弱哈希。

## 6. 权限判定逻辑

### 6.1 功能权限
用户 → 角色 → 权限码集合。每次接口请求在服务端校验是否拥有对应 `permission.code`。

### 6.2 数据权限
1. 取用户所有角色的 `data_scope`，按「并集、就宽不就窄」合并。
2. 解析为可见集合：
   - 全部：不拦截
   - 本组织及下级：`path LIKE 主属path + '/%'`
   - 仅本组织：仅主属部门
   - 仅本人：`created_by = 本人`
   - **本人 + 直属下属**：`created_by IN (本人, 直属下属...)`
   - 自定义部门：指定部门集合
3. 部门集合或人员集合注入查询（`dept_id IN (...)` 或 `created_by IN (...)`），必须**由服务端统一拦截器注入，不依赖前端传参**。
4. 超级管理员直接跳过数据范围。

## 7. 审计与登录日志

### 7.1 操作审计日志

| 字段 | 类型 | 说明 |

## 9. 非功能性需求

- **性能**：百级数据，普通索引 + 单表即可，组织树走 `path` 前缀匹配。
- **安全**：口令加盐哈希；功能权限与数据范围服务端校验，防越权；主管链禁止成环。
- **审计**：组织/角色/用户/权限变更记 operation_log，登录（含失败）记 login_log。
- **可维护**：初始化脚本内置超级管理员与默认角色，首次部署即可登录。

> **实施留痕（2026-09-11，V6.44：两个缺陷修复，由端到端测试用例发现）**：
> ① **组织树第 3 层及以下部门被静默丢弃（严重）**——`OrgService.tree()` 原实现为「先给全部节点建快照，再逐个挂子节点」，第二遍取到的是**第一遍的旧对象**，父节点永远只看到「还没有下级」的子节点，因此**三级及更深部门在 `/api/system/org/tree` 中根本不出现**（磁盘数据正常，仅接口返回缺失，前端部门管理树看不到）。最小复现：建 `A(parentId=0) → B(parentId=A) → C(parentId=B)`，接口只返回 A→B。修复：改为**深度降序装配**（先叶子后父级），保证父节点组装子列表时子节点已是最终形态；同级排序抽为常量 `NODE_ORDER`（`sort` 可空按 0、`id` 兜底）。修复后三级树正常返回。**影响面**：本工程「组织架构三级树」（V5.1 需求）此前实际只能显示两级。
> ② **管理员重置密码未做强度校验**——`UserService.resetPassword` 只依赖 `UserResetPasswordRequest` 的 `@Size(min=6)`，FR-V5-027④ 要求的「≥8 位含字母与数字」从未落地（新建用户的初始口令校验、个人中心改密码两者都有，唯独此处漏掉）。修复：抽出私有方法 `validatePasswordStrength()` 作为单一实现，`create` 与 `resetPassword` 共用；DTO 同步改为 `@Size(min=8, max=32)`；前端 `system.user.passwordPlaceholder` / `resetPasswordTips` 中英文案同步为「8-32 位，含字母与数字」。
> 两处修复均由 `backend/scripts/e2e-test.py` 用例覆盖并通过（211 项断言）。
