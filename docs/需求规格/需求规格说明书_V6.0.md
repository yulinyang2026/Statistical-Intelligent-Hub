## 1. 项目概述

### 1.1 建设背景

政府统计涉及多个产品线（部门统计、金融监管、统一报表、国资监管等），每个产品线又包含多个项目与模块/专题，信息分散在不同表格与文档中，存在查找困难、任务分配混乱、边界不清、进度不透明、责任人不明确、统计依赖人工等问题，需要统一平台承载。

### 1.2 建设目标

1. **模块、专题与项目分层管理**：统一关注怎么做、谁来做、什么时候做完。
2. **对象全生命周期信息统一维护**：模块、专题、项目各自的基础信息、子系统、进度、成员、任务、文档、状态构成单一数据源。
3. **计划驱动执行**：周计划 + 任务池，计划与实际对照，进度一屏掌握。
4. **权责清晰**：按组织架构分层授权（组员/组长/部门经理/系统管理员），数据范围与操作权限分级。
5. **可审计**：关键操作留痕，支持追溯。

### 1.3 范围界定


| 范围         | 内容                                                                                                                                                                              |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **本期范围** | 登录鉴权、数据看板、模块管理、专题管理、项目管理（含子系统）、任务管理、周计划管理、文档中心、对象内成员管理、系统管理（用户/组织/角色/基础数据/系统设置/操作日志）、界面交互框架 |
| **不在范围** | 全局成员管理页（V5.0 已移除）、月计划（V5.0 已移除）、移动端适配（待确认，见第 6 章）、公网部署方案（待确认，见第 6 章）                                                          |

### 1.4 术语表


| 术语                | 说明                                                                                                 |
| ------------------- | ---------------------------------------------------------------------------------------------------- |
| 模块（Module）      | 可持续交付的功能模块，有独立版本与生命周期，如「国企名录」「移动端」「自主数据管理」                 |
| 专题（Topic）       | 阶段性特有事项，如「前端性能优化」「文档库编写」                                                     |
| 项目（Project）     | 真实项目，有起止时间与预算，如「民政统计系统」，可挂靠一个模块或专题，包含多个子系统                 |
| 子系统（Subsystem） | 项目的下级拆分单元，项目与子系统为 1 对多关系；在列表中与项目以树形展示，具备同等操作能力            |
| 归属产品            | 基础数据字典：模块/项目归属的产品线，如部门统计、国资监管、轻量级统计、统一报表、业务组件库          |
| 模块分类            | 基础数据字典：模块的技术分类（BSP产品/组件/其他），可自行扩展                                        |
| 监督链              | 组织架构上下级关系：系统管理员→部门经理→组长→组员；「权限人员」= 本人 + 其监督子树内全部人员      |
| 组织架构树          | **部门 → 小组 → 成员**三级结构，用于组织展示；**监督链仍由用户「直属上级」字段构成**，两者互不替代 |
| 成本对象（哒咔）    | 财务成本核算单元编码，如`XM20260809CZBTYBB`                                                          |
| 所属产品型谱        | 项目运行的技术平台（仅项目侧使用）                                                                   |
| 重要级别            | 项目战略等级：A/B/C/D                                                                                |
| 待办任务            | 状态 ≠ 已完成的任务（待处理/进行中/受阻均计入），口径详见 3.6.4                                     |
| 我的待办            | **近三天**（今天 ~ 今天+3 天）内需完成、且分配给当前用户的任务，判定规则详见 3.2.2                   |
| 计划完成日期        | 任务字段`planDate`（YYYY-MM-DD），由周计划拖拽写回，可空                                             |
| 任务池              | 周计划中待编排的任务集合：**截止月份 = 当前查看周所在月**的全部任务（含已完成，已完成置灰不可拖）    |
| 干系人              | 参与项目/模块/专题但不是主责人                                                                       |
| RBAC                | 基于角色的访问控制                                                                                   |

> **术语变更说明**：原「产品（Product）」实体已拆分为「模块」「专题」两个独立实体；项目侧原「所属产品类别」字段更名为「归属产品」并改为引用基础数据字典。

## 4. 数据字典

### 4.1 实体关系

```
模块 Module  1 ──── N 任务 Task
专题 Topic   1 ──── N 任务 Task
项目 Project 1 ──── N 任务 Task
项目 Project 1 ──── N 子系统 Subsystem   （子系统 1 ──── N 任务，可选关联）

项目 Project N ──── 1 模块/专题（项目挂靠，belongType + belongId）

任务 Task、文档 Doc 均归属三者之一（项目/模块/专题），任务归属可为空（计划外临时任务）

用户 User（自引用：直属上级 supervisorId，构成监督链：组员→组长→部门经理→系统管理员）
部门 Department 1 ──── N 小组 Group 1 ──── N 用户 User（组织架构展示结构）

计划项 PlanItem N ──── 1 任务 Task（周计划的计划与实际记录）

基础数据类型 DictType 1 ──── N 基础数据字典项 BaseDictItem（被模块/项目引用）
操作日志 Log（弱关联，记录模块 + 目标名称）
```

### 4.2 关键实体字段

**模块 Module**：id、名称、**归属产品（字典引用）**、**分类（字典引用，moduleCategory）**、负责部门、负责小组、模块负责人、研发负责人（多）、测试负责人、成本对象、状态（字典引用：模块/专题状态，活跃/非活跃）、干系人、描述

**专题 Topic**：id、名称、负责部门、负责小组、专题负责人、研发负责人（多）、测试负责人、成本对象、状态（字典引用：模块/专题状态）、干系人、描述

> 专题不设「分类」「归属产品」字段，其余与模块一致。

**项目 Project**：id、名称、成本对象、重要级别、**归属产品（字典引用）**、所属产品型谱、负责部门、负责小组、销售负责人、项目经理、项目负责人、研发负责人、测试负责人、**项目状态（字典引用，人工维护）**、预算、开始/结束日期、干系人、挂靠对象（belongType + belongId）、描述

**子系统 Subsystem**：id、所属项目（projectId）、名称、负责人、排序

**任务 Task**：id、标题、说明、归属（projectId/moduleId/topicId 三选一，**可为空 = 计划外临时任务**）、执行人、优先级、截止月份（deadline，`YYYY-MM`）、预计工时、计划完成周（week）、**计划完成日期（planDate，YYYY-MM-DD，可空）**、状态、归属小组、子系统（subsystemId，可空，仅项目任务）、父任务（parentId，**仅两级**）

**计划项 PlanItem**：id、任务（taskId）、粒度（**当前仅使用「周」**）、周期键（如 `2026-W37`）、星期（1~7）、类型（计划/实际）、实际工时（hours，可空）、填写人、填写时间

**文档 Doc**：id、标题、归属（projectId/moduleId/topicId 三选一）、内容（Markdown）、更新人、更新时间、字数

**用户 User**：id、姓名、账号（唯一）、部门（dept 展示 + deptId 引用部门）、**小组（groupId，可空）**、角色、**直属上级（supervisorId，可空）**、邮箱、状态、创建时间

**部门 Department**：id、名称、排序、启用状态

**小组 Group**：id、名称、所属部门（deptId）、排序、启用状态

**角色 Role**：key（唯一）、名称、代表账号（rep，快速切换用）、数据范围（all 全部 / scope 本人+下属 / own 仅本人）、内置标记、权限点集合（perms）

**基础数据类型 DictType**：key（唯一）、名称、内置标记

**基础数据字典项 BaseDictItem**：id、字典类型（归属产品 / 项目状态 / 模块专题状态 / 模块分类 / …）、名称、排序、启用状态

**系统设置 Settings**：主题色（7 预设 + 自定义）、菜单背景色、菜单布局（left·top）、菜单风格（light·dark）、导航栏背景色、页面顶部颜色

**操作日志 Log**：时间、操作人、模块、操作对象、动作、详情

### B.1 触发范围与同步动作

任何改动（需求新增/修改/删除、口径调整、字段变更、交互变更，**以及纯技术缺陷修复**）完成后，均须同步本文档：


| 改动类型                                                     |  FR 条目  | 数据字典 | 版本变更记录                             | 版本号 |
| ------------------------------------------------------------ | :-------: | :------: | ---------------------------------------- | :----: |
| 需求/功能变更                                                | 修订/新增 |   同步   | 追加一行                                 |  递增  |
| 缺陷修复（不改需求口径，如接口路径错误、鉴权失效、样式错位） |   不动   |   不动   | 追加一行，标注「缺陷修复（无需求变更）」 |  递增  |

### B.2 版本号规则

- 小改动（**含缺陷修复**）递增次版本号：V6.0 → V6.1。
- 大范围结构性调整递增主版本号：V6.x → V7.0。
- 不引入三级修订号。

### B.3 技术方案设计文档

`技术方案设计文档.md` 仅在**技术选型、架构分层、存储或部署方案变更**时同步；日常功能改动与缺陷修复不更新。

### B.4 需求探询

- 存在歧义、多种合理理解，或影响结构/口径/交互的决策点时，先以问答形式（给出候选项与推荐项）确认后再实施，不猜测。
- 优先探询：术语与业务口径、范围边界（做/不做）、交互方式、权限差异、数据结构。
- 例外：改文案、改样式、明确指出的 bug 可直接执行。
- 每轮问答形成的结论须落入本文档。
- 用户提出的每一条需求（含未定稿）须先登记《16-待确认与非需求项.md》第 2 节「对话需求登记」，定稿后归位对应章节并留痕。

### B.5 文档维护约定

- 本文档为需求单一事实来源；早期版本（V5.3 及以前）的完整内容由附录 A 变更史追溯，不再单独保留副本。
- 新增需求写在**对应功能模块章节**，不得再按版本号新建补丁章节。
- 功能下线时直接删除或移入该章节的「已下线」小节，并注明移除版本。

### B.6 需求登记与留痕约定（2026-09-09 起强制）

用户每次提出的需求与每次改动，按下表流程执行，未同步文档视为任务未完成：

| 步骤 | 动作 |
| ---- | ---- |
| 1. 登记 | 用户每次提出的需求/改动意向，先在《16-待确认与非需求项.md》第 2 节登记一行（日期/描述/状态），未登记不得实施 |
| 2. 定稿 | 需求确认定稿后：涉及字段/枚举先改数据字典（第 4 章），再写入对应功能模块章节，并在条目内留痕（提出时间/来源/结论） |
| 3. 归档 | 登记表「归位结果」列注明去处（章节 / FR 编号 / 版本），然后删除该登记行 |
| 4. 版本 | 每次改动在版本变更记录追加一行并递增版本号（缺陷修复同样递增） |

例外：纯缺陷修复（不改需求口径）跳过 1~3，直接执行第 4 步。
